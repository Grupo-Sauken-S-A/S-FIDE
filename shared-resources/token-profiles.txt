# argentino (AC-ONTI). Fuente: documentación oficial SIU, AIF y fabricantes

#
# Este archivo es la ÚNICA fuente de verdad para la tabla de drivers: se
# copia como recurso a cada módulo que la necesita (token_slots_view,
# token_certificate_extractor, xml_signer_pkcs11, pdf_signer_pkcs11,
# s_fide_gui). Si se actualiza, alcanza con editar este archivo y recompilar.
#
# Formato (una línea por perfil, separado por "|", sin escapar nada):
#   marca|modelo|estrategia_hash|estado|ruta_windows|ruta_linux|ruta_macos|nombres_de_archivo_reconocidos(coma)
#
# estrategia_hash: "interno" (token expone CKM_SHA256_RSA_PKCS) |
#                  "externo" (token solo expone CKM_RSA_PKCS, requiere DigestInfo armado por software) |
#                  "externo-sin-confirmar" (se asume externo pero no está confirmado contra hardware real) |
#                  "desconocido"
# estado: recomendación de uso según AIF/SCBA (informativo, no bloquea nada)
#
# IMPORTANTE: esto es solo un hint de UX para autodetección y ayuda de
# selección de driver. El código de firma siempre reintenta en tiempo de
# ejecución (mecanismo combinado primero, hash externo como fallback) sin
# confiar ciegamente en esta tabla, porque el nombre de archivo puede cambiar
# entre versiones de middleware sin previo aviso.
#
# NOTA (confirmado con hardware real, ePass2003, 2026-08-30): "interno" en
# esta tabla significa "el intento de mecanismo combinado nunca falla en la
# práctica", no necesariamente que el token exponga CKM_SHA256_RSA_PKCS de
# forma nativa — el propio SunPKCS11 del JDK puede componer ese mecanismo de
# forma transparente sobre CKM_RSA_PKCS sin que el código de S-FiDE lo note.
# Para efectos prácticos (qué camino de código se ejecuta) el resultado es
# el mismo, por eso se clasifica igual.
